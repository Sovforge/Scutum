## [Unreleased]

### Added
- **Network policy and per-node firewall rule management** (`/network` → Network policies, closes #27): allow/deny rules between individual nodes or node groups, enforced as real `iptables` rules — but confined to a dedicated `SCUTUM_POLICY` chain hooked only off the WireGuard interface's own forwarded traffic (`FORWARD -i wg0 -o wg0 -j SCUTUM_POLICY`), never `INPUT`/`OUTPUT` or any other interface. A misconfigured policy, including default-deny, can therefore never lock out the hub's own management access, SSH, or any other host service — only mesh-to-mesh traffic is affected. `GET|POST /api/network/policies`, `PUT|DELETE /api/network/policies/{id}` for CRUD; `GET|PUT /api/network/policy-settings` for an opt-in default-deny toggle (off by default — unmatched traffic falls through unchanged until explicitly turned on). Every apply is a full flush-and-rebuild of the chain from the current policy set in priority order — simple to reason about, idempotent, and its only failure mode is a brief fully-open window rather than a stuck-closed one. Policies targeting a group expand to every member's resolved WireGuard mesh IP at apply time; a change is applied locally on the hub and relayed to every other node over the same HMAC-signed hub-to-node channel Docker/Kubernetes actions already use, both immediately on every CRUD mutation and via a background reconciler every 60 seconds (in case a node was offline or something external flushed the chain). Deny rules are logged via iptables `LOG` immediately before the `DROP`; a best-effort `journalctl`-tailing goroutine (degrades to a no-op if journald isn't available) parses those kernel log lines into real audit log entries. Every policy create/update/delete and every default-deny change is also audit-logged directly. New `network` read/write/admin permission (delete and the default-deny toggle require `admin`, matching the tier used for other destructive/high-blast-radius actions elsewhere). Scope notes: policies target nodes/groups by ID and resolve to concrete mesh IPs at apply time, rather than exposing a raw per-node "view/edit the actual iptables rules" UI; and policy templates (the issue's "isolate prod from dev" / "allow only hub egress" examples) aren't a separate backend concept — they're just policies, and an operator can build the same two rules directly from the form. Verified end-to-end against a real running backend: full CRUD, RBAC enforcement (operator can create/edit but not delete or touch default-deny), validation of node/group references, and a real audit trail. Rule-to-iptables-command translation (chain creation, the FORWARD hook, flush-and-rebuild, allow/deny/default-deny rendering, group fan-out) is covered by unit tests against a fake command runner; the actual host-level enforcement effect (dropping/allowing real packets) requires root and wasn't exercised live in this environment — `netpolicy.IsAvailable()`/apply failures are always best-effort and logged, never fatal, matching how WireGuard's own optional dependency is already handled.
- **Certificate management** (`/settings` → Certificates, closes #29): a real inventory and in-place rotation UI for the hub's own TLS server certificate and, if mTLS is configured (`CA_CERT_FILE`), the CA it uses to verify inbound client certs. `GET /api/admin/certificates` parses the actual cert/key files on disk and returns subject, issuer, serial, SANs, and days-until-expiry for each; `POST /api/admin/certificates/rotate` validates an uploaded PEM cert (+key, for the server slot), persists it to `CERT_FILE`/`KEY_FILE`/`CA_CERT_FILE`, and swaps it into the live TLS listener via `tls.Config.GetConfigForClient` — every new connection picks up the new cert immediately, with **no restart**. A daily background check fires a `certificate.expiring` webhook (configurable via `CERT_EXPIRY_WARN_DAYS`, default 30) when either cert is close to expiring, and every rotation is audit-logged (`CERTIFICATE_ROTATED`). This only applies to the manual `CERT_FILE`/`KEY_FILE` path — ACME-issued certificates already renew themselves automatically and are left untouched, and there's nothing to rotate when TLS is off. Note: this mesh has no per-node x509 certificates to inventory — node identity is a WireGuard key verified alongside an HMAC-signed request, not a client cert — so despite the issue's "per-node cert status" wording, there are exactly two cert slots here (hub server cert, hub CA), not one per node; the UI says so explicitly rather than fabricating per-node data that doesn't exist.
- **Secrets vault** (`/settings` → Secrets, closes #28): a KMS-backed named-secrets store, distinct from the Kubernetes Secret objects already managed under the relabeled "K8s Secrets" tab. Create, view (masked — no endpoint, including list, ever returns a plaintext value after creation), update, and delete named secrets with `/`-namespaced names (e.g. `prod/db/password`), each envelope-encrypted through the existing KMS provider abstraction (local/AWS/GCP/Vault) via `SetSecret`/`GetSecret`. New endpoints: `GET|POST /api/secrets`, `PUT|DELETE /api/secrets/{name}`, gated by a new `secrets` read/write/admin permission (seeded into the admin/operator/viewer roles like every other resource). Reference a secret from a container/pod env var, or a Docker Compose/Kubernetes YAML manifest, with `secret://<name>` — it's resolved to the real value on the hub immediately before deploying (`POST /docker/deploy`, `/docker/deploy-compose`, `/k8s/{ns}/apply`), including before proxying to a target node, since a remote node has no access to the hub's KMS. Every create/update/delete and every deploy-time resolution is audit-logged (`SECRET_CREATED`, `SECRET_UPDATED`, `SECRET_DELETED`, `SECRET_ACCESSED`).
- **File and config distribution across the mesh** (closes #32): push a file to a single node (`POST /api/nodes/{id}/files`) or every member of a group (`POST /api/groups/{id}/files`) over the same HMAC-authenticated hub-to-node channel Docker/Kubernetes actions already use — no SSH, no separate config-management tool. Destination paths are always relative and resolve under a managed directory on the *target* node (`<DATA_DIR>/distributed-files/…`), never an arbitrary absolute host path — Scutum typically runs as root with `NET_ADMIN`, so an unrestricted write-any-path primitive would be a real privilege-escalation vector; both `..` traversal and absolute paths are rejected outright. Optional opt-in template substitution (`{{.NodeIP}}`, `{{.NodeName}}`, `{{.NodeID}}`, plus any caller-supplied variables) lets one config template render differently per target node — off by default so binary uploads like TLS certs are never accidentally run through `text/template`. Every attempt (per-node, even for a group) is tracked in a new `file_transfers` table with a real per-node status (`pending`/`in_progress`/`done`/`failed`) and surfaced in a transfer history table on the Nodes page, alongside the distribution form itself; every attempt is also audit-logged. Verified end-to-end: real file delivery with correct permissions and content, real rejection of absolute and traversal paths, real per-node template rendering, real group fan-out, and unit tests for the path-safety and templating logic.
- **Resource Monitoring page** (`/monitoring`, new sidebar entry): fleet-wide per-node view of live CPU/memory/disk usage as color-coded bars, 1/5/15-minute load averages, and a 60-minute CPU sparkline, refreshed every 30 seconds. Uses the existing `GET /api/system/stats` and `GET /api/system/stats/history` endpoints — this closed a real gap where the frontend rewrite had dropped a page whose backend was still fully live and functional.
- **System settings** (`/settings` → General / Mesh / Nodes / Auth, `GET|PUT /api/settings`, admin-only): a real persisted policy object (`system_settings` table) backing what used to be a static, no-op mock in all four sub-tabs. General covers a cluster name and region (display only) and a log level that's applied to the running server immediately on save via `Logger.SetLevel` — no restart needed. Mesh covers the WireGuard MTU (applied live to `wg0` via `ip link set mtu`, best-effort — harmless if WireGuard isn't up) and the default persistent-keepalive used for newly added peers; listen port and address stay fixed at setup time since changing them live would tear down every peer's tunnel. Nodes adds a default role for the enrollment form and a "require approval" toggle: when on, nodes created via `POST /api/nodes` start out `pending` instead of `approved` (a new `nodes.status` column) and must be approved (`POST /api/nodes/{id}/approve`) or rejected (`POST /api/nodes/{id}/reject`, which discards the request) from the Nodes page before they count as real fleet members. Auth adds a per-cluster MFA requirement and a configurable session timeout (replaces the previous hardcoded 24 h JWT expiry) — the Auth sub-tab's Single Sign-On card also now lists real configured SSO providers (`GET /api/auth/sso/providers`) instead of a static "coming soon" placeholder. **Every field defaults to its previous hardcoded behavior (or off, for the two policy toggles), so upgrading requires no action** — nothing changes until an admin visits Settings and turns something on. When MFA enforcement is turned on, a user who logs in correctly but hasn't enabled MFA yet still gets a token (`mfa_setup_required: true` in the login response) and is routed straight to Account's MFA setup instead of being locked out — this is deliberate, so an admin can never turn the policy on and then lock themselves out of their own account.
- **Kubernetes Secrets management** (`/settings` → Secrets): now manages real Kubernetes Secret objects instead of a local-only mock. List (`GET /api/kubernetes/secrets`), create (`POST /api/kubernetes/{ns}/secrets` — Opaque with arbitrary key/value pairs, TLS from pasted cert/key PEM, or Docker registry from server/username/password/email, assembled into a real `.dockerconfigjson` client-side), delete (`DELETE /api/kubernetes/{ns}/secrets/{name}`), and rotate (`POST /api/kubernetes/{ns}/secrets/{name}/rotate` — Opaque only, replaces every existing data key with a fresh random value; TLS/Docker-registry secrets reject rotation with a 400 since their keys hold structured data, not independent tokens). Secret values are never returned by any of these endpoints — list and get only ever expose key names, matching the metadata-only disclosure the mock already had.
- **Kubernetes Deployments tab** (`/kubernetes` → Deployments): now lists every Deployment across every reachable cluster (`GET /api/kubernetes/deployments`) with an inline replica editor and real Scale (`POST /api/kubernetes/{ns}/deployments/{name}/scale?replicas=N`) and rolling-Restart (`POST /api/kubernetes/{ns}/deployments/{name}/restart`) actions, replacing the "isn't wired up yet" placeholder — the backend already supported both, the UI just didn't call them.
- **Terraform and Pulumi providers**, now published as standalone repos rather than living under `contrib/`: [terraform-provider-scutum](https://github.com/Sovforge/terraform-provider-scutum) (`registry.terraform.io/Sovforge/scutum`, built with the Terraform Plugin Framework) and [pulumi-scutum](https://github.com/Sovforge/pulumi-scutum) (bridged from the Terraform provider via `pulumi-terraform-bridge`, published to npm/PyPI/NuGet/Maven/Go). Both manage the same five resource types: nodes (register hub/remote nodes), groups (node groups and membership), federation peers (inter-hub WireGuard tunnels), webhooks (webhook endpoint subscriptions), and users (user accounts and role assignment). Authenticate via API key — set it in the provider config or the `SCUTUM_API_KEY` environment variable. See each repo's README for usage examples and releasing instructions.
- **Alert rules and event log** (`/settings/alerts`): Threshold-based alerting with five built-in conditions — `cpu_percent`, `mem_percent`, `disk_percent`, `node_offline` (minutes since last WireGuard handshake), and `handshake_age`. Rules are evaluated every 60 seconds by a background goroutine and automatically fire `alert.fired` / `alert.resolved` webhook events when thresholds are crossed or cleared. Rules can be silenced for a configurable window (default button: 4 h) without deletion. The settings page provides a rule builder modal, severity badges (info / warning / critical), enable/disable toggle, per-rule silence, and a live event log with acknowledgement. New endpoints: `GET|POST /api/alerts/rules`, `PUT|DELETE /api/alerts/rules/{id}`, `PUT /api/alerts/rules/{id}/silence`, `GET /api/alerts/events`, `POST /api/alerts/events/{id}/acknowledge`. Three new DB tables (`alert_rules`, `alert_events`) added across SQLite, PostgreSQL, and MySQL schemas.
- **Backup and restore UI** (`/settings/backup`): Admin page for creating on-demand database snapshots and restoring from a previous one. Supports SQLite (WAL checkpoint + gzip copy), PostgreSQL (`pg_dump`), and MySQL (`mysqldump`) — matching the existing `scripts/backup.sh` logic but driven from the UI. New endpoints: `GET|POST /api/admin/backups` (list and trigger), `GET /api/admin/backups/{id}/download` (stream the gzip file), `DELETE /api/admin/backups/{id}` (remove), `POST /api/admin/backups/{id}/restore` (in-place restore with restart notice for SQLite). Backup files are stored in `<DATA_DIR>/backups/` and named `scutum-<timestamp>.<driver>.gz`. A "Backup & Restore" link has been added to the Settings sidebar.
- **Grafana dashboard and OTel trace export** (`contrib/grafana/scutum-dashboard.json`): Pre-built Grafana dashboard with 8 panels covering mesh node counts, HTTP request rate, 4xx/5xx error rate, CPU/memory/disk usage over time, mesh sync latency (p50/p95), and healer check rate. Import it via Grafana's "Import dashboard" UI and point it at the Prometheus datasource scraping `/api/metrics`. Three new Prometheus gauges are also exposed: `scutum_node_cpu_percent`, `scutum_node_mem_percent`, and `scutum_node_disk_percent`, updated every 60 seconds by the existing resource stats background goroutine. OTel span export is now configurable: set `OTEL_EXPORTER_OTLP_ENDPOINT` (e.g. `http://collector:4318`) to forward all internal API spans to an external OTLP/HTTP collector in 5-second batches with no additional dependencies. Trace IDs were already propagated through the audit log; the exporter adds the external forwarding path.
- **Resource monitoring dashboard** (`/monitoring`): Fleet-wide per-node view showing live CPU, memory, and disk usage as colour-coded bar gauges (green → amber → red at 70% / 90%), load averages (1m / 5m / 15m), and an inline SVG CPU sparkline covering the last 60 minutes. Stats are collected every 60 seconds by a background goroutine using a zero-dependency `/proc`-based collector (`/proc/stat`, `/proc/meminfo`, `/proc/loadavg`, `syscall.Statfs`) and stored in a rolling 24-hour `node_stats` table across all three DB drivers (SQLite, PostgreSQL, MySQL). Live stats and history are available via `GET /api/system/stats` and `GET /api/system/stats/history`; both endpoints support `X-Target-Node` proxying so the hub can reach remote nodes. The sidebar now includes a "Monitoring" navigation entry.
- **IronKey / USB share export**: Emergency Recovery Key shares can now be saved directly to a USB drive (e.g. IronKey) via the File System Access API (`showSaveFilePicker`). Each share gets its own `.erk` file. Falls back to `<a download>` for browsers without File System Access API support (Firefox, Safari). USB import (`showOpenFilePicker`) is also supported when loading shares for reissue or recovery. See `/settings/recovery`.
- **Recovery Keys settings page** (`/settings/recovery`): Admin page for generating a fresh set of ERK shares from the current master key and reissuing existing shares when a share holder leaves or a share is compromised. Per-share USB export and USB-load-from-file for input shares.
- **Node groups UI**: Nodes page now includes a Node Groups section. Groups can be created, deleted, and expanded inline to add or remove member nodes via a dropdown selector.
- **Settings sidebar for sub-pages**: Federation, Webhooks, SCIM, and Recovery Keys pages now render with the shared settings navigation sidebar (`SettingsShell` component), consistent with the rest of the settings area.
- **Hub federation**: Link two independent Scutum instances so their WireGuard meshes can route to each other. Adding a federation peer (`POST /api/federation/peers`) registers the remote hub's public key and mesh CIDR as a WireGuard peer with persistent keepalive; removing it tears the tunnel down. Status is tracked per peer (`pending` / `connected` / `error`).
- **Node groups and labels**: Tag nodes with arbitrary key=value labels (`PUT /api/nodes/{id}/labels`) and organise them into named groups (`GET|POST /api/groups`). Groups track membership explicitly; `GET /api/groups/{id}/nodes` lists all member nodes. Useful for targeting bulk operations by environment, region, or role.
- **CRA compliance report** (`GET /api/compliance/report`): Generates a structured report covering users, mesh topology, audit log summary, security incidents, encryption details, key management status, and audit retention policy — aligned with EU Cyber Resilience Act (CRA) 2024/2847. Available in `json` (default), `csv` (raw audit log), and `text` (human-readable) formats via the `?format=` query parameter.
- **Webhook notifications**: HTTP webhook delivery for mesh events (`node.enrolled`, `node.offline`, `node.online`, `healer.service_restart`, `audit.critical`, `user.created`, `auth.sso_login`). Each delivery is HMAC-SHA256 signed via `X-Scutum-Signature`. Includes a test endpoint (`POST /api/webhooks/{id}/test`) and one automatic retry on failure. Managed via admin-only CRUD at `GET|POST /api/webhooks` and `GET|PUT|DELETE /api/webhooks/{id}`.
- **SCIM 2.0 user provisioning**: Full RFC 7644 implementation at `/scim/v2/Users` supporting create, read, update, patch (including `active=false` deprovisioning), and delete. Uses dedicated long-lived bearer tokens (managed via `POST /api/scim/tokens`) separate from user JWTs. Compatible with Microsoft Entra ID, Okta, and any SCIM 2.0 IdP.
- **Audit log forwarding**: Background worker ships audit log entries every 30 seconds to configured external endpoints in JSON or CEF (ArcSight/QRadar) format. Managed via admin-only CRUD at `GET|POST /api/audit/forwarders` and `GET|PUT|DELETE /api/audit/forwarders/{id}`.
- **Single Sign-On (SSO)**: OIDC/OAuth2 login support for Microsoft Entra ID (Azure AD / Office 365), GitHub, Authentik, Keycloak, and any generic OIDC provider. Providers are enabled via environment variables (`SSO_<PROVIDER>_CLIENT_ID` / `CLIENT_SECRET` / `ISSUER_URL`) and only appear on the login page when configured. On first SSO login, the account is linked by email or created automatically. New endpoints: `GET /api/auth/sso/providers` (public — returns enabled providers), `GET /api/auth/sso/{provider}` (initiates login), `GET /api/auth/sso/{provider}/callback` (exchanges code and issues JWT).
- **Automatic TLS via ACME / Let's Encrypt**: Set `ACME_DOMAIN` and `ACME_EMAIL` to enable automatic certificate provisioning and renewal. Scutum starts an HTTP-01 challenge server on port 80 and redirects all plain-HTTP traffic to HTTPS. Set `ACME_STAGING=true` to use the Let's Encrypt staging environment. When unset, the existing manual cert (`CERT_FILE`/`KEY_FILE`) and plain-HTTP fallback behaviour is unchanged.
- **Kubernetes operator** (`operator/`): CRD-based cluster management with `ScutumHub` and `ScutumNode` custom resources. The operator reconciles StatefulSets, Services, RBAC, and ConfigMaps for hub and edge deployments; automatically enrolls edge nodes into the mesh via the hub enrollment API; and manages a bootstrap Secret per node containing WireGuard config and HMAC credentials. Requires `scutum.io/v1alpha1` CRDs installed via `operator/config/crd/`.
- **Operator bootstrap endpoint** (`GET /api/operator/bootstrap`): Admin-only endpoint that returns the hub's WireGuard public key, listen port, HMAC key (base64), and mesh CIDR. Used by the operator to configure edge nodes without requiring direct access to the hub's secrets volume.
- **Helm chart** (`helm/scutum`): Production-ready Helm chart deploying Scutum as a StatefulSet with a `ClusterIP` service for the API/UI and a `LoadBalancer` service for the WireGuard UDP port. Includes: TLS init container (self-signed cert generation on first start), Gateway API `HTTPRoute` template, `ClusterRole`/`ClusterRoleBinding` for Kubernetes in-cluster access, PVC-backed storage for `/data` and `/secrets`, and `NET_ADMIN` capability wiring for WireGuard.
- **NAT roaming via WireGuard keepalive**: The mesh now relies on WireGuard's native `persistent-keepalive = 25` to track endpoint changes transparently — no application-layer polling required. When an edge node changes networks, WireGuard's keepalive packets update the kernel's peer endpoint automatically. The healer's `FreshEndpoint` callback reads the live endpoint from `wg show endpoints` (with the database as a fallback) so re-adds always use the current address. On hub startup, `registerOwnEndpoint` performs a one-shot registration; the previous 2-minute periodic re-registration ticker has been removed.
- **Hub API address auto-derivation**: The hub API address for a remote node is now inferred from its `AllowedIPs` when the field is a single `/32` (or `/128`) host route, so operators no longer need to fill in a separate "Hub API address" field for standard mesh configurations. Explicit values still take priority; the WireGuard endpoint is used as a last resort.
- **`cmd/internal/roaming` package**: Extracted `NodeAPIBase`, `CallRegisterEndpoint`, and `HubMeshIP` from `package main` into an importable package so they can be unit-tested and reused outside the main binary.
- **`GetPeerEndpoint` utility**: New `utils.GetPeerEndpoint(iface, publicKey)` reads the live endpoint for a given peer directly from the WireGuard kernel state via `wg show <iface> endpoints`, and is exposed through the `wireguard.Service` interface.

### Changed
- **The old Nuxt/Vue frontend has been removed.** `frontend-v2` (React + Vite) is renamed to `frontend/` and is now the only frontend — it had reached full feature parity (including two pages, Resource Monitoring and Kubernetes Secrets/Deployments management, that were either missing or non-functional in the rewrite until this pass) and fixed several bugs the old app either had too or introduced nowhere. **Two things need awareness on upgrade, though neither needs any configuration change:**
  - **Everyone will be logged out once.** The old frontend stored its session in a cookie (`auth_token`); the new one uses `localStorage` (`scutum_token`). These aren't shared, so upgrading invalidates every active browser session — just log back in, nothing else is affected (no data loss, no server-side session state to migrate).
  - **Some URLs changed.** `/auth/login` and `/auth/forgot` moved to `/login` and `/forgot`. Most `/settings/*` sub-pages (webhooks, SCIM, recovery, secrets, backup, alerts, RBAC) collapsed into tabs under one `/settings` URL; `/settings/federation` moved to the Network page; `/nodes/groups` and the per-node `/nodes/{id}` detail view merged into the Nodes page; `/observability/{logs,metrics,traces}` merged into Observability's tabs (they were already just redirects to it in the old app). Bookmarks and any external links to these old paths now redirect automatically to the right place instead of 404ing — see "Old-path redirects and a real 404 page" below — but a bookmark's saved label may still say the old name.
  - Nothing else changes: same single Go binary, same database, same API, same WireGuard mesh, and the Terraform/Pulumi providers, SCIM, and webhook integrations are all frontend-independent and unaffected.
- **Old-path redirects and a real 404 page**: the frontend previously had no catch-all route at all — any unmatched URL (a typo, an old bookmark, anything) rendered a blank white page. It now has a proper "Page not found" page, plus explicit redirects for every old Nuxt-app URL listed above, so upgrading doesn't silently break saved links.
- **Node type simplified**: The `combined` node type has been removed. Valid node types are now `hub` and `remote` only. Existing `peer`, `edge`, and `combined` rows are migrated to `remote` on first startup. The node enrollment modal, filters, stats strip, and default role in Node Defaults settings have all been updated accordingly.
- **Setup page — Hub API address is optional**: The "Hub API address" field is now labelled optional and its placeholder explains it is auto-derived from the Hub allowed IPs. The hint no longer mentions periodic re-registration.
- **Nodes page — API address auto-derived on enroll**: The "API address" field in the Enroll Peer modal is optional; when left blank the value is derived from the node's `AllowedIPs` (strips the `/32` prefix). The Enroll button no longer requires the field to be non-empty. `document.execCommand('copy')` replaced with the standard Clipboard API.
- **Node detail page — accurate WireGuard labels**: The "Endpoint" row is renamed "API address" to reflect that the displayed value is the mesh IP / API address, not the UDP WireGuard endpoint. The hardcoded "Listen port: 51820" is replaced with "—" since the port is not returned by the API.

### Fixed
- **`GET /api/operator/bootstrap` always 500'd on every real hub install**: it read the HMAC key from the secret named `hub_hmac_key`, but a hub instance never stores one under that name — that's the name a *remote* install stores the hub's key under locally after receiving it during setup. A hub's own key lives under `sync_hmac_key`. Found while building file distribution (#32), which needed this same endpoint to hand a new node its mesh credentials.
- **SSO login silently failed to sign the user in**: the OIDC/OAuth2 callback (`HandleCallback`) redirected to `/#sso-token=<jwt>` — the root path, which is a protected dashboard in the old Nuxt frontend but a public marketing page in this rewrite, with no code anywhere to read the token back out of the URL hash. A user completing SSO would land on the marketing page with a valid, unused token sitting in the address bar instead of being logged in. Now redirects to `/login#sso-token=<jwt>`, where the hash is actually consumed. Also switched from a hardcoded 24 h token lifetime to the same configurable session timeout the password-login path uses.
- **Personal API key creation was unreachable for every user**: `POST /api/auth/keys` was registered as a public route (alongside `/auth/login`, `/auth/register`) with no auth middleware, but its handler reads the caller's identity from auth claims and returns `401 unauthorized` when they're absent — so the endpoint always 401'd, for every user, including admins. Moved under the authenticated route group, matching the adjacent `GET /auth/tokens` / `DELETE /auth/tokens/{id}` routes it's meant to work alongside. Verified end-to-end: a real personal API token can now be created, listed, and revoked.
- **Kubernetes/Docker delete actions were unreachable for every user**: `DELETE /api/kubernetes/{ns}/pods/{name}` and `DELETE /api/docker/containers/{id}` were gated behind a `"delete"` permission action that was never seeded for any role (`nodes`/`docker`/`kubernetes`/etc. only ever seed `read`/`write`/`admin`), so the permission check failed unconditionally and both endpoints always returned `403 forbidden` — including for admins. Both now require the `admin` tier for their resource, matching every other destructive endpoint in the API (`DELETE /nodes/{id}`, `DELETE /users/{id}`, `DELETE /webhooks/{id}`, etc., all already used `admin`).
- **Kubernetes scale/restart/secret-rotate silently failed against a real cluster**: `models.Meta` didn't carry `resourceVersion`, so the GET-modify-PUT round trip used by `ScaleDeployment`, `RestartDeployment`, and the new secret-rotate endpoint dropped it on every read, and the Kubernetes API server rejects an update whose object has no `resourceVersion`. Confirmed against a real `kind` cluster: scale/restart/rotate all failed until `resourceVersion` was added to `Meta` and round-tripped through the existing GET → mutate → PUT flow (no handler code changes needed once the field existed).
- **Frontend `request()` helper rejected successful empty-body responses**: it only tolerated an empty body on `204 No Content`, but several handlers (Scale, Restart, Create Secret, and others) succeed with `200`/`201` and `Content-Length: 0` — `res.json()` throws on empty text regardless of status, so these calls surfaced as failures in the UI (toast: "Scale failed") even though the request had already succeeded server-side. `request()` now reads the body as text first and only parses it as JSON when non-empty, which also retroactively fixed the previously-shipped Kubernetes Deployments tab's Scale and Restart buttons (verified against a real cluster: both were silently broken before this fix).
- **SQLite schema**: `node_groups`, `node_group_members`, and `audit_forwarders` tables were truncated (missing closing `);` and missing `description`/`created_at` columns on `node_groups`). The same truncation existed across SQLite, MySQL, and PostgreSQL schemas and caused a fatal `near "CREATE": syntax error` on startup.
- **useApi.ts EOF**: `downloadComplianceReport` was missing its closing `}`, causing all subsequent function declarations (Webhooks, SCIM, SSO, audit forwarders) to be parsed inside that function body, producing an unexpected-EOF build failure.
- **Docker routes return 503 in Kubernetes**: All Docker API endpoints now check for the socket at `/var/run/docker.sock` before executing. When the socket is not mounted (the default in Kubernetes), the response is `503 Service Unavailable` with a clear JSON message instead of a raw dial-failure `500 Internal Server Error`. A `requireDocker` middleware in the router handles this uniformly across all 15 Docker endpoints.
- **Compose deploy error when Docker CLI absent**: `POST /docker/deploy-compose` now checks for the `docker` CLI binary via `exec.LookPath` and returns a `503` with a descriptive message if it is not found in `PATH`, rather than returning an opaque error from the failed `exec.Command` call.

## [1.0.0] — 2026-05-23

### Added
- **Multi-stage Dockerfile**: Single-command build producing an Alpine-based binary image with an embedded CycloneDX SBOM generated by Syft at build time.
- **Hub-to-Node Proxying**: All Docker and Kubernetes API actions can now be forwarded to remote nodes by setting the `X-Target-Node: <node-id>` request header. Inter-node requests are authenticated with an HMAC-SHA256 signature (`X-Scutum-Hub-Sig` + `X-Scutum-Hub-Ts`) derived from the shared `sync_hmac_key`, so edge nodes never need to trust a browser JWT.
- **Leader Election**: Hub instances now use a DB-backed lease (`hub_leases` table) to elect a single active leader, preventing IP conflicts when multiple Hub containers share the same database.
- **Hub Interface Restoration**: On startup, if the system is already set up, Scutum automatically restores the `wg0` WireGuard interface from configuration saved in the database, enabling seamless container restarts and hot-standby failover.
- **Rate Limiting**: IP-based token-bucket rate limiter (2 req/s, burst 5) applied to all public authentication endpoints (`/auth/login`, `/auth/register`, `/setup`, `/auth/forgot-password`) to mitigate brute-force attacks. Includes automatic TTL-based eviction to prevent memory growth.
- **Graceful Shutdown**: The API server now catches `SIGINT`/`SIGTERM` and performs an ordered shutdown: HTTP server drain → Healer stop → Pusher stop → DB close.
- **Audit Log Retention**: Automated background pruning of `audit_logs`, `system_logs`, and `traces` tables. Defaults to 365 days (configurable via `AUDIT_RETENTION_DAYS`) to align with EU Cyber Resilience Act recommendations.
- **Admin Password Complexity**: Initial admin credentials must meet a 12-character minimum with uppercase, lowercase, number, and special-character requirements.
- **Docker Compose Healthcheck**: Added `healthcheck` directive to `docker-compose.yaml` via `GET /api/health`.
- **Backup Script**: Added `scripts/backup.sh` supporting SQLite (WAL checkpoint), PostgreSQL (`pg_dump`), and MySQL (`mysqldump`) with automatic retention purging (`BACKUP_RETAIN_DAYS`, default 90 days).
- **mTLS Support**: Enforces mutual TLS on incoming Hub connections when `CA_CERT_FILE` is configured; injects client certificates into outgoing edge sync (`HTTPEdgeSink`).
- **Multi-Database Support**: Automatic driver selection based on `DATABASE_URL` — PostgreSQL, MySQL, or SQLite.
- **Prometheus Metrics**: HTTP request counter (`scutum_http_requests_total`), healer health checks (`scutum_healer_checks_total`), and mesh sync latency (`scutum_mesh_sync_latency_seconds`) exposed at `/api/metrics`.
- **TOTP / MFA**: TOTP-based multi-factor authentication with recovery codes for all user accounts.
- **KMS Integration**: Local, AWS KMS, GCP KMS, and HashiCorp Vault key providers for envelope encryption of all secrets.
- **Role-Based Access Control**: Fine-grained permissions model with role assignment per user.
- **Plugin System**: Native Go plugin support with a route registrar for extending the API.
- **WireGuard Auto-Install**: Automatic installation of `wireguard-go` when the kernel module is absent.

### Changed
- Module path renamed from `orcistrator` to `scutum`; database and storage directory paths updated accordingly.
- Frontend runs as a pure SPA (`ssr: false`) to eliminate hydration mismatches between server-rendered and client-rendered state.
- All frontend API calls use relative paths (`/api/...`) so the UI works correctly regardless of the host or port it is served from.
- WebSocket terminal URLs now derive from `window.location` with an `/api` prefix, fixing connections when the app is proxied or served on a non-default port.
- Prerender step skips `/api/**` routes to prevent build-time 502 errors when the backend is not available during `nuxt generate`.
- Mesh summary (`/api/network/mesh-summary`) counts the local node in `total` and `healthy`, giving an accurate view of the full mesh including the hub itself.
- `WGChecker` interface methods now accept a `context.Context`; a `ContextRunner` adapter bridges the existing context-free `utils.CommandRunner` to the new interface.

### Fixed
- `registerEdges` goroutine now retries up to 5 times with exponential back-off to handle transient startup failures.
- Rate limiter state is evicted every 5 minutes for IPs not seen recently, preventing unbounded memory growth.
- Healer: check timeout context is now correctly passed to `PeerHandshakeAge` instead of being silently discarded, preventing goroutine hangs when the `wg` CLI is slow.
- Healer: service restart backoff is now enforced — unhealthy services are no longer restarted on every tick regardless of the configured backoff window.
- Healer: `PeerHandshakeAge` no longer panics when a public key is shorter than 8 bytes.
- Healer: `Stop()` waits for the heal-loop goroutine to finish before returning.
- Pusher: `Stop()` resets the edge map to an empty map instead of `nil`, preventing a panic on any subsequent `Register()` call.
- Pusher: `HTTPEdgeSink.Send` uses `bytes.NewReader` instead of `strings.NewReader(string(body))`, eliminating a redundant allocation.
- Mesh test: removed host-side WireGuard UDP port mappings that caused bind failures on hosts already running a WireGuard interface; container-to-container traffic uses the Docker bridge directly.
- Mesh test: Stage 4 crash-recovery is now deterministic — `docker wait` ensures the container has fully exited before `docker start` is called, removing the dependency on the Docker restart policy.
